# 05-Gateway / Messaging / 推送问题

> 🎯 一句话结论：这一页不是教你重新接一遍 Telegram、飞书、企业微信或钉钉，而是集中回答“为什么消息收不到、为什么 gateway status 不正常、为什么平台已经配了却不回、为什么会话在消息平台里像乱掉了”这类高频问题。

如果你现在最焦虑，只先记住一句：

> Gateway 问题最常见不是“平台完全坏了”，而是平台凭据、gateway 运行方式、会话重置规则、允许列表或平台侧配置边界没有对齐。

## 这页主要回答什么

这一页集中回答这几类高频问题：

- 为什么平台明明配了，但消息收不到？
- 为什么 `hermes gateway status` 看起来不正常？
- 为什么 gateway 在前台能跑，装成服务后反而不对？
- 为什么消息平台里像开了新会话、上下文接不上？
- 为什么平台已经能聊天，但 slash 命令、语音、权限或重置行为看起来不对？

## 先做一个最小判断

如果你现在完全不知道问题卡在哪，先做这 4 步：

```bash
hermes gateway setup
hermes gateway status
```

如果你当前是前台运行，还要直接观察：

```bash
hermes gateway
```

这组最小动作的目的不是立刻修好，而是先判断：

- 是平台根本没配好
- 是 gateway 没真的在运行
- 是运行了但平台侧没把消息送进来
- 还是消息进来了，但会话 / 权限 / 重置规则不符合预期

## ❓FAQ 正文

<a id="faq-status-not-ok"></a>

### 🌐 01｜为什么 `hermes gateway status` 看起来不正常？

> ❓ 问题：为什么 `hermes gateway status` 看起来不正常？
>
> 💡 先说结论：最常见原因不是平台坏了，而是 gateway 根本没起来、服务没安装成功，或者你当前看的不是实际在跑的那一份 gateway。

最常见原因是：

- gateway 没有真正启动
- 你以为装成服务了，但服务其实没成功装好
- 当前 profile 不是你以为的那个 profile
- 平台配置写了，但运行中的 gateway 没读取到那份配置

🔎 先做什么：

先明确你当前用的是哪一种方式：

- 前台运行：

```bash
hermes gateway
```

- 服务化运行：

```bash
hermes gateway status
```

先分清“我现在是在看前台进程”，还是“我现在是在看系统服务”。

🚦 什么时候该跳转：

- 如果连 gateway 都没真正跑起来，先留在本页
- 如果 gateway 正常，但平台配置本身明显有误，回对应入口页

<a id="faq-service-vs-foreground"></a>

### 🌐 02｜为什么前台能跑，装成服务后反而不对？

> ❓ 问题：为什么前台能跑，装成服务后反而不对？
>
> 💡 先说结论：这通常不是“平台突然坏了”，而是前台运行和服务化运行读取的环境、profile、路径或系统服务状态并没有完全对齐。

最常见原因是：

- 你前台启动时在正确 profile 里，服务却不是
- 服务读取不到你以为的环境变量或配置
- 你已经改了配置，但服务没重启
- 你把“前台日志正常”和“服务状态正常”误当成同一件事

🔎 先做什么：

优先确认：

- 你当前到底在比较哪两个运行方式
- 配置改完以后是否真的重启过服务
- 当前 profile 下的 gateway 配置是不是和服务实际用的是同一份

🚦 什么时候该跳转：

- 如果你现在根本不需要常驻服务，先前台跑通再说
- 如果你必须服务化，再继续留在本页查运行边界

<a id="faq-message-not-arriving"></a>

### 📩 03｜为什么平台已经配了，但消息还是收不到？

> ❓ 问题：为什么平台已经配了，但消息还是收不到？
>
> 💡 先说结论：最常见不是 Hermes 不收消息，而是平台凭据、机器人权限、事件订阅、allowed users 或平台侧入口没真的打通。

最常见原因是：

- 平台凭据不完整
- 平台侧机器人 / 应用没有真正开启到位
- 你在错误的聊天对象里发消息
- 平台侧事件 / 接入方式和 Hermes 当前适配器路线不一致

Messaging Gateway 文档已经明确：

- gateway 负责接平台消息
- 会按 per-chat session 分发给 AIAgent
- 先要有正确的平台适配配置，消息才能进来

🔎 先做什么：

先把问题拆成 3 层：

1. 平台侧入口是否真的建好了
2. gateway 是否真的在运行
3. 消息是否真的送到了正确 chat / user / bot

🚦 什么时候该跳转：

- 如果你怀疑是飞书、企业微信、钉钉具体接法问题，回对应入口页
- 如果你怀疑是 gateway 根本没接住消息，留在本页

<a id="faq-connected-no-reply"></a>

### 📩 04｜为什么平台看起来连上了，但就是不回复？

> ❓ 问题：为什么平台看起来连上了，但就是不回复？
>
> 💡 先说结论：这类问题最常见不是“机器人完全没连上”，而是消息已经到了某一层，但后面被权限、会话状态、模型层异常或停止状态卡住了。

最常见原因是：

- gateway 连上了，但当前 chat 无权限
- 消息到了，但当前 agent 在 provider / model 层报错
- 会话状态被 reset / stop / access control 影响
- 你把“已连接”误当成“已可回复”

🔎 先做什么：

优先先判断：

- 是所有消息都不回
- 还是只有某个平台 / 某个 chat 不回
- 是完全静默
- 还是回复很慢、像没反应

如果只是“回得慢”，那也可能根本不是 gateway 层，而是模型响应慢。

🚦 什么时候该跳转：

- 如果最终看起来更像 provider / model 层，回 [03-模型 / Provider / 自定义 endpoint 问题](./03-模型 Provider 与自定义 endpoint 问题.md)
- 如果只是某个平台具体配置错，回对应入口页

<a id="faq-session-reset"></a>

### 💬 05｜为什么消息平台里像总在开新会话？

> ❓ 问题：为什么消息平台里像总在开新会话？
>
> 💡 先说结论：最常见原因不是会话系统坏了，而是 gateway 本来就有按平台 / chat 分会话的逻辑，加上 reset policy 会让你感觉“上下文像断了”。

Messaging Gateway 文档已经明确：

- gateway 维护的是 per-chat sessions
- 会话可以按 daily / idle / both 等策略重置

这意味着：

- 不同聊天对象，本来就不是同一会话
- 同一聊天对象，也可能因为空闲时间或每日重置而换新会话

🔎 先做什么：

先不要先怪“记忆丢了”，先问：

- 我现在是不是换了 chat
- 当前平台是不是触发了 reset policy
- 我期待的是会话连续，还是长期记忆连续

🚦 什么时候该跳转：

- 如果你怀疑是会话理解错了，留在本页
- 如果你怀疑是 profile / memory / config 层混用，再去配置 / profiles 页

<a id="faq-slash-different"></a>

### 💬 06｜为什么 slash 命令在消息平台里表现和 CLI 不一样？

> ❓ 问题：为什么 slash 命令在消息平台里表现和 CLI 不一样？
>
> 💡 先说结论：因为消息平台里的 slash commands 是 gateway 暴露出来的那一层，不等于你在本地交互式 CLI 里的完整体验。

Messaging Gateway 文档列出了 in-chat commands，例如：

- `/new`
- `/reset`
- `/model`
- `/provider`
- `/retry`
- `/undo`
- `/status`
- `/stop`
- `/help`

这说明：

- 消息平台里确实支持一批命令
- 但它不等于完整本地 CLI 的所有交互细节
- 你不能把“消息平台里的命令手感”完全等同于本地 terminal 里的交互感受

🔎 先做什么：

先分清：

- 你现在要的是 in-chat 控制命令
- 还是本地 CLI 里的完整交互能力

🚦 什么时候该跳转：

- 如果你真正想学的是本地交互，回 [04-CLI / TUI / 会话问题](./04-CLI TUI 与会话问题.md)
- 如果你要的是平台里的命令边界，留在本页

<a id="faq-access-control"></a>

### 💬 07｜为什么权限、allowlist、pairing 看起来不对？

> ❓ 问题：为什么权限、allowlist、pairing 看起来不对？
>
> 💡 先说结论：最常见原因不是 gateway 随机拒绝，而是当前 access control 策略和你脑中的使用方式根本不是同一套规则。

Messaging Gateway FAQ / 文档已经说明：

- gateway 支持 allowlists
- 支持 DM pairing
- 不同平台可有不同 access control 预期

最常见混淆是：

- 你以为任何人都能用，实际开了 allowlist
- 你以为这是公共 bot，实际走的是 first-user pairing
- 你以为群聊和私聊行为一样，实际入口策略不同

🔎 先做什么：

先回答三个问题：

1. 我现在希望谁能访问
2. 我现在的平台是 DM 还是群聊
3. 当前策略是 open、allowlist，还是 pairing 类模式

🚦 什么时候该跳转：

- 如果你已经确认是 access control 预期不对，先留在本页
- 如果你怀疑是平台侧机器人权限没开够，回对应入口页

<a id="faq-voice-cron-multi"></a>

### 🔊 08｜为什么语音消息、定时任务或多平台一起用时容易混乱？

> ❓ 问题：为什么语音消息、定时任务或多平台一起用时容易混乱？
>
> 💡 先说结论：因为一旦进入语音、cron、多平台并行，问题就不再只是“这个 bot 会不会回”，而变成“消息从哪来、会话落在哪、结果送到哪、哪个平台在消费哪条链路”的组合问题。

最常见混淆是：

- 你以为 cron 没跑，实际是结果发到了别的平台
- 你以为语音失败，实际是文本正常、音频转换链路没通
- 你以为多个平台共用同一会话，实际是 per-chat 分开的

🔎 先做什么：

一旦进入这类混合问题，先不要一次改 5 个地方。
先拆：

1. 平台链路通不通
2. 文本消息通不通
3. 语音或 cron 是不是额外复杂度
4. 结果到底交付到了哪里

🚦 什么时候该跳转：

- 如果你主要在查 cron，后续更适合看自动化页
- 如果你主要在查消息平台收发，继续留在本页

### 🔊 09｜什么时候该把问题当成 gateway，本质上其实是入口页或平台配置问题？

> ❓ 问题：什么时候该把问题当成 gateway，本质上其实是入口页或平台配置问题？
>
> 💡 先说结论：只要你现在的问题已经涉及“平台怎么创建、怎么拿凭据、怎么选接入模式、平台权限怎么开”，那就不该继续把它当纯 gateway 问题硬调。

下面这些情况，更适合回入口页：

- 你还没确定该走哪种平台接法
- 你还没拿到正确凭据
- 你还没完成平台侧机器人 / 应用创建
- 你其实在比较飞书、企业微信、钉钉、个人微信的路径差异

🔎 先做什么：

先问自己：

- 我现在是在查 Hermes gateway 运行层
- 还是在查平台侧接入方式本身

只要这个问题没分开，就会越调越乱。

🚦 什么时候该跳转：

- 如果是平台侧接入问题，回 [03-国内入口 / 01-总览](../03-国内落地/03-国内入口/01-总览.md)
- 如果平台已经配好，只是 Hermes gateway 行为不符合预期，留在本页
