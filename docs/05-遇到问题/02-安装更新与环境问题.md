# Hermes Agent 安装与更新排障：Windows、PATH 和下载错误

<a id="hermes-agent-安装与更新排障gitpython-和环境错误"></a>

安装失败或更新失败，先区分终端命令、运行环境与桌面 backend：记录完整错误和版本，再按本页症状分流。命令已经能运行而桌面仍显示 connecting，转到[桌面启动与连接排障](/docs/start/personalize/desktop-app)；VPS 和容器升级看[VPS 安装与维护](/docs/start/practical/vps-self-hosting)。

> 一句话结论：这一页只处理“命令起不来、装不上、更新后变怪、环境边界混乱”这类问题。只要你还没确认 `hermes` 命令本身是否正常，就先不要跳去查模型、Gateway、Tools。

如果你现在很急，先记住：
> 先确认是不是命令层 / PATH / shell / 终端类型问题；不要一上来就删目录重装。

## 🔎 搜索收录速答

安装、更新和环境问题通常先查三件事：当前 Hermes 二进制来自哪里、当前 shell 读到的配置目录是哪一个、Node/Python/系统依赖是否和官方要求一致。排障时优先运行诊断命令，再区分是安装失败、升级后版本不一致，还是 PATH 与 profile 混乱。相关问题可以继续看[配置 / Profiles / 环境隔离](/docs/issues/config-profiles-environment)和[CLI TUI 与会话问题](/docs/issues/cli-tui-session)。

先保存第一条下载错误，确认失败的是官方脚本、依赖包、桌面运行时还是模型请求。它们可能使用不同域名和下载器，不能用统一换源步骤保证修复。先检查终端代理、证书、地址和安装渠道；具体下载排障见 [FAQ 11](#faq-china-mirror)。

## 🧪 先做最小判断

先记录 OS/架构、shell、安装渠道与命令路径。Bash/Zsh 用 `command -v hermes`，PowerShell 用 `Get-Command hermes`；然后检查版本和诊断，不要同时乱改配置：

```bash
command -v hermes
hermes --version
hermes doctor
```

怎么理解结果：
- `command -v hermes` 都找不到：优先还是安装 / PATH / shell 问题
- `hermes --version` 跑不起来：还没进入模型层
- `hermes --version` 正常、`hermes doctor` 开始报 provider / model：大概率已经该跳到 [03-模型 / Provider / 自定义 endpoint 问题](./03-模型 Provider 与自定义 endpoint 问题.md)

## ✅ 先做什么：5 步排查清单

按这个顺序排，最不容易越改越乱：

1. 确认你是不是在受支持环境里
   - 按固定标签平台表核对 Linux、macOS Apple Silicon、Windows 10/11、WSL2 和 Android（Termux）
   - 原生 Windows 为 Tier 1，部分功能仍有平台限制；WSL2 是另一条受支持路线
2. 确认安装归属与官方渠道：桌面包、源码安装器或 Docker
3. 确认 `git`、`curl`、网络至少能工作
4. 重新打开终端，核对当前渠道的命令目录与 PATH；不要跨 Windows/WSL 复用路径
5. 只有前 4 步都没问题，才讨论手动安装或重装

## 📌 先记住这 4 个官方基线

<a id="1标准安装命令只有这一条"></a>

### 1）按系统与安装渠道选择官方入口

```bash
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
```

以上适用于 Linux/macOS/WSL2/Termux 的 Bash 路线。原生 Windows 在 **PowerShell** 使用：

```powershell
iex (irm https://hermes-agent.nousresearch.com/install.ps1)
Get-Command hermes
hermes --version
hermes doctor
```

macOS/Windows 也可选择[官方桌面安装器](https://hermes-agent.nousresearch.com/desktop)。固定标签安装说明还列出开发者源码路线；Docker 更新按镜像和容器流程处理。先确认安装归属，不向现有安装叠加另一渠道。


<a id="2标准更新命令只有这一条"></a>

### 2）源码安装更新先检查配置迁移

```bash
hermes update
```

如果更新过程中跳过了新配置迁移，立刻补：

```bash
hermes config check
hermes config migrate
```

<a id="3官方只要求你先有-git"></a>

### 3）依赖按平台和构建方式检查

```bash
git --version
```

固定标签的非 Windows 安装器以 Git 为前提；Linux 还需 `curl`、`xz-utils`，桌面源码构建需要 `g++` 或 `build-essential`。安装器会处理的依赖包括：
- Python 3.11
- Node.js
- ripgrep
- ffmpeg

所以装不上时，不要一上来就手动补一堆依赖；先确认是不是环境或网络链路问题。

### 4）更新后先做最小验收，不要靠感觉判断

```bash
hermes --version
hermes doctor
hermes gateway status
```

怎么看：
- `hermes --version` 正常：至少命令层活着
- `hermes doctor` 正常：基础环境大概率没坏
- `hermes gateway status` 正常：如果你本来就在跑消息平台，更新没有把服务层带坏

## ❓FAQ

<a id="faq-command-not-found"></a>

### 01｜执行就报 `hermes: command not found`

❓ 问题

执行 `hermes` 就报 `command not found`。

💡 先说结论

最常见不是“完全没装上”，而是 shell 没 reload、PATH 没生效，或者你还停留在旧终端窗口。

🔎 先做什么

以下命令用于 Linux/macOS/WSL2/Termux 的 Bash/Zsh。原生 Windows 请重新打开 PowerShell，用 `Get-Command hermes` 检查入口，并按本页“按系统与安装渠道选择官方入口”核对安装目录与 PATH；不要把 `~/.local/bin` 当成 Windows 的统一安装位置。

```bash
source ~/.bashrc
```

如果你用的是 zsh：
```bash
source ~/.zshrc
```

然后再查：
```bash
command -v hermes
ls ~/.local/bin/hermes
```

如果你确认文件在，但命令还是找不到，临时补 PATH：
```bash
export PATH="$HOME/.local/bin:$PATH"
hermes --version
```

🚦 什么时候该跳转

- `hermes --version` 还是完全跑不起来：继续留在本页
- `hermes --version` 正常了，但开始报模型 / Key / endpoint：跳到 [03-模型 / Provider / 自定义 endpoint 问题](./03-模型 Provider 与自定义 endpoint 问题.md)

### 02｜安装脚本一开始就失败

❓ 问题

安装脚本刚开始执行就失败，或者根本拉不下来。

💡 先说结论

先别怀疑 Hermes 本体，先查命令、Git、网络、代理。

🔎 先做什么

以下是非 Windows 的 Bash 脚本排查。原生 Windows 使用本页前面的 PowerShell `install.ps1` 路线；完整应用安装包、源码 bootstrap 与远端 Light 分别按对应渠道排查，不能统一套用 Bash。

```bash
git --version
curl --version
```

官方 Bash 源码安装命令：
```bash
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
```

优先检查这几件事：
- 你执行的是不是官方完整命令
- 当前终端能不能正常访问官方安装源
- 代理是不是只让浏览器通，不让终端通
- 机器上是不是连 `git` 都没装好

🚦 什么时候该跳转

- `git` / `curl` 本身异常：先修基础环境
- 安装器能跑，但后面卡在 provider / model：跳到 [03-模型 / Provider / 自定义 endpoint 问题](./03-模型 Provider 与自定义 endpoint 问题.md)

<a id="faq-windows-wsl"></a>

### 03｜Windows 为什么总装不对

❓ 问题

我明明在 Windows 上执行了命令，但安装过程总是很怪。

💡 先说结论

Windows 10/11 原生安装和 WSL2 都是官方支持路线。v2026.9.24 平台表将原生 Windows 列为 Tier 1，部分功能仍受 Windows 功能矩阵限制。

🔎 先做什么

- 原生安装在 PowerShell 用官方 `install.ps1`；WSL2 在 Linux shell 用 `install.sh`。
- PowerShell 用 `Get-Command hermes` 检查命令来源；Bash/Zsh 用 `command -v hermes`。
- 不把 Bash 的 `source`、`export` 和 Linux 路径直接复制到 PowerShell。
- 记录版本、安装渠道与数据目录，不仅因为身处 Windows 就迁移或重装。

🚦 什么时候该跳转

- 你还没把基础安装主线走通：可先回看 [04-把 Hermes 装上去](../01-从这开始/01-先跑起来/04-把 Hermes 装上去.md)
- 你已经在 WSL2 且命令正常，只是模型报错：跳到 [03-模型 / Provider / 自定义 endpoint 问题](./03-模型 Provider 与自定义 endpoint 问题.md)

<a id="faq-update-broken"></a>

### 04｜更新之后突然变怪，是不是新版本坏了

❓ 问题

更新之后突然不对劲，我要不要先怀疑新版本坏了。

💡 先说结论

不一定。更新后异常，最常见还是旧终端没关、shell 没 reload、PATH 指到了旧位置，或者更新其实已经引入了新的配置项，你跳过了迁移。

🔎 先做什么

```bash
hermes update
hermes config check
hermes config migrate
command -v hermes
hermes --version
hermes doctor
```

如果你本来就在跑消息平台，再补一条：
```bash
hermes gateway status
```

按结果拆：
- `command -v hermes` 不对：先修 PATH / shell
- `hermes config check` 提示缺配置：先完成迁移，再继续判断
- `hermes --version` 正常、`doctor` 报 provider / model：已经不只是安装问题
- `gateway status` 异常：说明更新可能影响了服务层，但不等于安装器坏了
- 两个都正常：优先去查后续层，而不是继续在这里怀疑安装器

补充一个 v2026.5.29.2 之后的判断口径：官方该版本只修复了 wheel / sdist 包里 bundled `plugin.yaml` manifests 没有随包发布的问题。如果你是在升级后遇到“插件清单 / bundled plugin manifest 缺失”这类异常，先执行 `hermes update` 更新到 v2026.5.29.2 或更高版本，再重新跑 `hermes doctor`；不要把它误判成 provider、API Key 或 endpoint 配置错误。

补充一个 v2026.7.7.2 之后的判断口径：官方该版本（v0.18.2）修复了 WhatsApp 桥接 (Baileys) 的依赖锁定问题。如果你在安装或执行 Docker 构建时遇到由于 git 链接导致的依赖拉取失败（尤其涉及 Baileys），请务必更新到 v2026.7.7.2 或更高版本。此版本将依赖指向了发布的 npm 包，大大提升了国内和受限环境下的安装可靠性。

如果更新过程像卡住了，可以看日志：
```bash
tail -f ~/.hermes/logs/update.log
```

🚦 什么时候该跳转

- provider / model 报错：跳到 [03-模型 / Provider / 自定义 endpoint 问题](./03-模型 Provider 与自定义 endpoint 问题.md)
- CLI / 会话行为异常：跳到 [04-CLI / TUI / 会话问题](./04-CLI TUI 与会话问题.md)
- 消息平台恢复不了：跳到 [05-Gateway / Messaging / 推送问题](./05-Gateway Messaging 与推送问题.md)

### 05｜怎么判断现在还是安装层问题

❓ 问题

我现在到底还在安装层，还是其实已经进入模型 / 配置层了？

- 明显进入鉴权 / 模型 / endpoint：跳到下一页

### 10｜明明装过 `node` / `pyenv` / `asdf`，为什么 Hermes 还是像没看到

❓ 问题

我明明已经有 Node、Python 或版本管理器，但 Hermes 运行时还是像没看到这些工具。

💡 先说结论

这通常不是 Hermes "忘了识别"，而是你的环境初始化只写在 `~/.bashrc`，但登录 shell 读的是 `~/.profile` 或 `~/.bash_profile`。

🔎 先做什么

- 先确认你现在依赖的是不是 `nvm`、`pyenv`、`asdf`、`cargo` 这类 shell 初始化工具
- 如果这些初始化只写在 `~/.bashrc`，把关键 PATH / init 也补到 `~/.profile` 或 `~/.bash_profile`
- 改完以后，重新开一个终端窗口，再跑一次：

```bash
which node
which python3
command -v hermes
hermes --version
```

🚦 什么时候该跳转

- 这些基础命令都已经正常，后面只剩 provider / model：跳到 [03-模型 / Provider / 自定义 endpoint 问题](./03-模型 Provider 与自定义 endpoint 问题.md)
- 你真正卡的是 CLI 交互或会话恢复：跳到 [04-CLI / TUI / 会话问题](./04-CLI TUI 与会话问题.md)

### 11｜国内安装卡在 GitHub / pip / Playwright 下载，怎样定位？

先保存第一条错误和实际请求地址，再按下载器分流：

| 失败层 | 先检查 | 处理边界 |
|---|---|---|
| 官方脚本 / Release | 终端代理、TLS、官方地址、OS/架构 | 不把不明第三方代理域名直接替换进安装脚本执行 |
| Python 依赖 | 具体工具是 uv 还是 pip、错误包名、使用中的索引 | pip 配置不一定影响 uv；定位前不全局改源 |
| Node / npm | 是否需要该依赖、实际 registry 与下载日志 | 只调整已确认的下载器，保留原配置与恢复步骤 |
| Playwright 浏览器 | 浏览器下载与系统库错误分别判断 | 下载成功不能代替系统依赖安装，按对应版本官方说明处理 |
| 桌面包 / Docker | 包渠道、镜像标签、运行时与构建日志 | 不把源码构建排障步骤套到完整桌面包或容器 |

镜像运营方会进入软件供应链的信任范围。只有确认具体下载器支持某项镜像配置后，再做可恢复的针对性调整。本页未完成镜像安全或国内可用性实测，不提供成功率保证。

安装命令恢复后，模型请求失败应转到[Provider 与 endpoint 排障](/docs/issues/provider-endpoint)。

<a id="faq-fast-mirror-skill"></a>

<a id="12fast-mirror-skill-是什么hermes-官方推荐用吗"></a>

### 12｜是否应该用社区换源 Skill 自动修复？

不要把自动换源作为新手安装的默认前置步骤。先确认失败的下载器、当前配置和来源，再审阅工具会修改哪些文件、使用哪些域名以及如何恢复。不能仅凭社区宣传认定安全、可用或能修复全部安装错误。

Hermes 自身还没启动时，依赖 Hermes 执行的 Skill 也不能替代基础安装排障。先看 [FAQ 11](#faq-china-mirror)，需要了解 Skills 再看[自定义 Skills](/docs/start/practical/custom-skills)。

<a id="faq-doctor-fields"></a>

### 13｜`hermes doctor` 输出字段都代表什么？怎么根据它判断问题在哪？

❓ 问题

跑完 `hermes doctor`，看到一堆打勾打叉的项，不知道每项代表什么。

💡 先说结论

`hermes doctor` 是 Hermes 的环境健康检查命令，输出按层分段，每段对应一个可能的故障层。看懂字段含义，就能直接定位问题。

🔎 字段对照表

| 输出区段 | 检查内容 | 出现 ❌ 通常意味着 |
|---------|---------|------------------|
| **Python Runtime** | Python 版本、uv 是否就绪 | 安装链路有问题，回 FAQ 02 |
| **Hermes Installation** | hermes 二进制路径、版本、是否有多个冲突 | PATH 没生效，回 FAQ 01 |
| **SOUL.md / USER.md** | 助手人格和用户档案是否存在、路径是否正确 | 文件路径错位，跳 FAQ 14（profiles 页） |
| **Gateway Status** | 是否在跑 systemd 服务、各平台（Telegram/Discord）连接 | 服务层问题，跳 [05-Gateway](./05-Gateway Messaging 与推送问题.md) |
| **systemd Linger** | 用户级服务能否开机自启 | linger 没开，`sudo loginctl enable-linger $USER` |
| **Tools / Toolsets** | 当前可用工具列表 | toolsets 配置不全，[07-Toolsets 参考](../06-reference/07-Toolsets%20参考.md) |
| **MCP Servers** | 已配置的 MCP server 连接状态 | MCP 配置错，[08-MCP 配置参考](../06-reference/08-MCP%20配置参考.md) |
| **Provider / Model** | 当前选中的 provider、model、API Key 是否设置 | 跳 [03-模型 / Provider](./03-模型 Provider 与自定义 endpoint 问题.md) |

**最常见三种组合判断**：

- 已通过的诊断项 → 只证明对应检查；模型、网络和可选工具仍需分别验收
- Python / Hermes 红 → 安装层问题，留在本页
- Provider / Gateway 红 → 已经离开安装层，跳对应故障页

🚦 什么时候该跳转

- doctor 显示 Provider / Model 有问题：跳 [03-模型 / Provider](./03-模型 Provider 与自定义 endpoint 问题.md)
- doctor 显示 Gateway 有问题：跳 [05-Gateway / Messaging](./05-Gateway Messaging 与推送问题.md)
- doctor 显示 SOUL.md 路径错位：跳 [07-配置 / Profiles 与环境隔离问题](./07-配置 Profiles 与环境隔离问题.md#faq-soul-path)
