# 04-CLI / TUI / 会话问题

> 🎯 一句话结论：这一页不是教你重新学一遍 Hermes CLI，而是集中回答“为什么界面显示不对、为什么按键没反应、为什么会话像没记住、为什么看起来卡住了”这类最常见的 CLI / TUI / 会话问题。

如果你现在最焦虑，只先记住一句：

> 只要 `hermes` 能启动，很多 CLI / TUI / 会话问题都不是“完全坏了”，而是交互方式、会话恢复方式、终端环境或上下文边界没有对齐。

## 这页主要回答什么

这一页集中回答这几类高频问题：

- 为什么 CLI / TUI 显示乱码、错位、emoji 不正常？
- 为什么输入 `/` 没看到命令、快捷键像没反应？
- 为什么退出后感觉会话丢了、前文没记住？
- 为什么 `--continue` / `--resume` 看起来恢复不对？
- 为什么界面像卡住了、没反应、很久不出字？

## 先做一个最小判断

如果你现在完全不知道问题卡在哪，先做这 4 步：

```bash
hermes version
hermes
```

进入后，再判断：

- 输入 `/`，看看命令补全是否出现
- 退出后试一次：

```bash
hermes --continue
```

这组最小动作的目的不是立刻修好，而是先判断：

- 是显示 / 终端问题
- 是交互 / 命令补全问题
- 是会话恢复方式没用对
- 还是模型响应 / provider 本身在拖慢交互

### 📟 01｜为什么 CLI / TUI 看起来乱码、错位、emoji 不显示？

> ❓ 问题：为什么 CLI / TUI 看起来乱码、错位、emoji 不显示？
>
> 💡 先说结论：最常见原因不是 Hermes 会话坏了，而是终端字体、终端宽度、emoji 渲染或当前终端环境本身不适合显示这些字符。

最常见原因是：

- 当前终端字体对 emoji / 特殊符号支持不好
- 终端窗口太窄，导致界面换行错位
- 你当前在很受限的终端里（某些远程面板 / 简化终端）
- 你把“显示问题”误当成“功能问题”

🔎 先做什么：

优先先做最小判断：

- 把终端窗口拉宽一点
- 换一个更正常的本地终端再试一次
- 先试最基础的 CLI，而不是一上来就把显示问题归咎于 TUI

如果只是字符不好看，但：

- `hermes` 能启动
- 能正常输入
- 能正常返回内容

那更像是显示层，不是功能层。

🚦 什么时候该跳转：

- 如果只是字符显示怪，但功能都正常，先不用跳页
- 如果你连 `hermes` 都进不去，回 [02-安装 / 更新 / 环境问题](./02-安装更新与环境问题.md)

### 📟 02｜为什么我明明进了 Hermes，但界面看起来很怪？

> ❓ 问题：为什么我明明进了 Hermes，但界面看起来很怪？
>
> 💡 先说结论：很多“界面很怪”的问题，本质上是你在用的不是你以为的那个入口，或者你把 classic CLI 和 `--tui` 的表现混在一起了。

Quickstart 已经明确：

- `hermes` = classic CLI
- `hermes --tui` = modern TUI

也就是说，有些体验差异不是 bug，而是入口本来就不同。

🔎 先做什么：

先分别试这两个入口：

```bash
hermes
```

```bash
hermes --tui
```

然后只回答一个问题：

- 是两个都怪
- 还是只有其中一个看起来怪

这样你才能判断：

- 是终端显示问题
- 是特定入口问题
- 还是你只是还不熟悉界面结构

🚦 什么时候该跳转：

- 如果 classic CLI 正常、只有 TUI 体验怪，先把问题当成交互层问题留在本页
- 如果两个入口都异常，而且连基础聊天都跑不顺，回模型 / Provider 页交叉判断

<a id="faq-slash-not-showing"></a>

### ⌨️ 03｜为什么输入 `/` 没有看到命令或补全？

> ❓ 问题：为什么输入 `/` 没有看到命令或补全？
>
> 💡 先说结论：最常见原因不是 slash commands 消失了，而是你不在交互式会话里、当前输入状态不对，或者你把 shell 命令和 Hermes 内部斜杠命令混在一起了。

CLI Commands Reference 已经明确：

- slash commands 是在 **interactive CLI** 里用的
- 输入 `/` 会出现命令补全
- 命令大小写不敏感

🔎 先做什么：

先确认你是在这里：

```bash
hermes
```

而不是：

```bash
hermes chat -q "..."
```

因为 `chat -q` 这种单次命令，本来就不是给你弹 slash 补全用的。

然后在交互界面里直接输入：

```text
/
```

看是否出现命令补全。

🚦 什么时候该跳转：

- 如果你发现自己其实一直在用非交互命令，就留在本页修正使用方式
- 如果进入交互界面后依旧完全没有 slash 行为，再继续留在本页看交互问题

<a id="faq-ctrlc-exit"></a>

### ⌨️ 04｜为什么 Ctrl+C、清屏、退出这些动作和我想的不一样？

> ❓ 问题：为什么 Ctrl+C、清屏、退出这些动作和我想的不一样？
>
> 💡 先说结论：很多人把“退出当前会话”“结束当前进程”“清掉终端显示”当成一件事，但它们不是同一个动作。

根据已有中文页：

- `Ctrl+C`：退出当前使用 / 当前会话交互
- `clear`：只是清掉终端画面
- 会话本身是否还能恢复，要看你后面怎么继续

🔎 先做什么：

先把这 3 件事分开理解：

1. 我现在是想退出交互
2. 我现在只是想清屏
3. 我现在是想下次继续回来

只要这三件事没分开，你就很容易把正常行为误判成“会话没了”。

🚦 什么时候该跳转：

- 如果你的困惑核心是“退出后怎么继续回来”，直接看本页后面的会话问题
- 如果你的困惑核心是“CLI 根本没进来”，回环境页

---

<a id="faq-session-feels-lost"></a>

### 💾 05｜为什么退出以后感觉前文丢了？

> ❓ 问题：为什么退出以后感觉前文丢了？
>
> 💡 先说结论：最常见原因不是历史真的消失了，而是你没有用正确方式继续原会话，而是重新开了一个新会话。

很多人会把这两件事混掉：

- 重新启动 Hermes
- 继续上一次会话

这两个动作不是同一个动作。

🔎 先做什么：

如果你只是想继续最近一次会话，先用：

```bash
hermes --continue
```

如果你要恢复指定会话：

```bash
hermes --resume 会话ID
```

而不是直接再次运行：

```bash
hermes
```

因为直接重新进 `hermes`，更像是进入新的交互入口，不自动等于恢复你脑中那一段会话。

🚦 什么时候该跳转：

- 如果你真正的问题是“恢复哪个会话”，继续看本页下一题
- 如果你发现自己从没用过 `--continue` / `--resume`，先不用往别页跳

---

<a id="faq-continue-resume"></a>

### 💾 06｜为什么 `--continue` / `--resume` 恢复出来的不是我想要的会话？

> ❓ 问题：为什么 `--continue` / `--resume` 恢复出来的不是我想要的会话？
>
> 💡 先说结论：最常见原因不是 Hermes 乱恢复，而是你对“最近一次”“指定 ID”“按名字续接”的差别没有分清。

CLI Commands Reference 已经说明：

- `--continue`：继续最近一次会话
- `--resume <id>`：恢复指定会话
- `-c "名字"`：按名字续接该 lineage 的最近会话

也就是说，这三种不是等价命令。

🔎 先做什么：

如果你不确定会话 ID，先去列出会话，再恢复：

- 先看已有会话列表
- 再决定是继续最近一次，还是恢复指定那一条

不要把“我以为它应该恢复 A”当成命令本身已经精确指定了 A。

🚦 什么时候该跳转：

- 如果你只是没分清命令语义，留在本页
- 如果会话列表本身异常、历史像没写进去，之后再考虑配置 / profile 层问题

---

<a id="faq-context-not-remembered"></a>

### 💾 07｜为什么它看起来“不记得前文”，但又不是完全新会话？

> ❓ 问题：为什么它看起来“不记得前文”，但又不是完全新会话？
>
> 💡 先说结论：很多时候这不是“会话彻底丢了”，而是上下文窗口、会话长度、当前切回的会话节点，或者你预期中的“长期记忆”和“当前会话上下文”不是一回事。

常见混淆是：

- 会话继续 ≠ 永远完整带着所有前文
- 当前会话上下文 ≠ memory / skills / profile

也就是说，它可能是在正确会话里，但你期待它像“完整无限记忆”那样回忆所有细节，这本来就不是一回事。

🔎 先做什么：

先判断：

- 我是不是回到了正确会话
- 我期待的是“恢复最近对话”，还是“拥有长期记忆”
- 我的问题究竟是会话继续，还是 profile / memory 没生效

🚦 什么时候该跳转：

- 如果你怀疑是 profile、memory、config 层问题，后续更该去配置 / profiles / 自己造东西相关页
- 如果只是会话恢复预期不对，先留在本页

<a id="faq-stuck"></a>

### 🛑 08｜为什么界面像卡住了，输入后很久没反应？

> ❓ 问题：为什么界面像卡住了，输入后很久没反应？
>
> 💡 先说结论：很多“假死”并不是 CLI 真挂了，而是模型响应慢、provider 在超时边缘、工具调用在执行，或者当前终端没有把状态变化显示得很明显。

最常见原因是：

- 当前模型响应本来就慢
- provider / endpoint 在高延迟状态
- 工具调用正在执行，但你以为没动
- 当前终端显示让你误以为没反馈

🔎 先做什么：

先判断：

- 是完全不能输入
- 还是能输入但迟迟不出结果
- 是所有请求都慢，还是只有某一类请求慢

如果只是“很久没出字”，不要第一反应就把它判成 CLI 坏了。

🚦 什么时候该跳转：

- 如果慢的是所有请求，更可能是模型 / provider 问题，回 [03-模型 / Provider / 自定义 endpoint 问题](<./03-模型 Provider 与自定义 endpoint 问题.md>)
- 如果只是 Gateway 消息链路慢，不要停在本页，回入口 / Gateway 相关页

### 🛑 09｜什么时候该把问题当成 CLI / TUI，会什么时候其实是模型 / Provider 在拖慢？

> ❓ 问题：什么时候该把问题当成 CLI / TUI，会什么时候其实是模型 / Provider 在拖慢？
>
> 💡 先说结论：如果问题主要体现在“看起来慢、像没反应、结果很久才出来”，很多时候更该先怀疑 provider / model，而不是 CLI 外壳本身。

一个很实用的分界线是：

- 如果问题是“显示怪、补全不出、快捷键不顺、恢复方式混乱”，更像 CLI / TUI / 会话层
- 如果问题是“能正常发出请求，但结果慢、报鉴权、报 endpoint、报模型”，更像 provider / model 层

🔎 先做什么：

先问自己：

1. 我的问题是交互方式怪，还是结果链路慢？
2. 我的问题在“输入前”，还是“发送后”？
3. 我卡在界面，还是卡在模型响应？

只要这三件事分开，你就不容易把外壳问题和推理链路问题混在一起。

🚦 什么时候该跳转：

- 如果是 provider / model / endpoint 层，回 [03-模型 / Provider / 自定义 endpoint 问题](<./03-模型 Provider 与自定义 endpoint 问题.md>)
- 如果你现在已经确认只是 CLI / TUI / 会话层，继续留在本页即可
