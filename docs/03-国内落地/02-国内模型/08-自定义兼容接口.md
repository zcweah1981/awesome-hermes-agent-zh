# 08-自定义兼容接口

> 🎯 一句话结论：如果你手上已经有一个 OpenAI-Compatible 的中转网关、第三方聚合层，或者你准备直接接本地推理服务（如 LM Studio、Ollama），那么“自定义兼容接口”就是最省重复劳动的一条路线——前提是你已经有一个稳定入口。

这一页沿用前面几页更清楚的写法：先讲适合谁、这条路到底值不值得选、不同入口怎么分，再讲 Hermes 里如何把 `base_url`、`api_key` 和模型名正确映射起来。

## 🚀 接入主线图

![自定义兼容接口路线图](./assets/custom-endpoint-modules-cliproxy-v10-16x9-preview.png)

先看图，自定义兼容接口不是“第一次用 Hermes 的默认起点”，而是当你已经拥有一个 **OpenAI-Compatible** 入口时的适配方案。

这页真正讲的是三类入口：

- **本地 OpenAI 兼容服务**：例如 LM Studio、Ollama
- **第三方聚合中转层**：例如 OneAPI、NewAPI 或自建转发池
- **企业内网 / 私有网关**：统一做鉴权、路由、审计或限流

## ✨ 这条路适合谁

- 你手里已经有兼容接口，不想重新迁移整套工作流
- 你要对接的是本地模型服务、企业自建网关或第三方聚合层
- 你已经知道自己为什么需要中间层，而不是只想第一次跑通 Hermes
- 你想把多个模型入口统一成一个 `base_url`
- 你希望在 Hermes 里用一套 `custom endpoint` 方式接各种兼容 OpenAI 的服务

## 🧭 先看最短决策

| 你的情况 | 建议 |
|---|---|
| 你只是第一次跑通 Hermes，还没有现成兼容层 | 不要先走这条，优先回看原生 provider 页 |
| 你本地已经在跑 LM Studio | 走 **本地兼容接口** |
| 你本地已经在跑 Ollama | 走 **本地兼容接口** |
| 你已经有 OneAPI / NewAPI / 自建聚合池 | 走 **第三方聚合中转层** |
| 你在企业里需要统一鉴权、审计、限流 | 走 **企业私有网关** |

如果你只想记住一句话：

- **没有现成入口 → 不要先选自定义兼容接口**
- **已有稳定 OpenAI-Compatible 入口 → 直接走 custom endpoint**

## 💡 这条路真正值不值得选

这页最重要的，不是“它高级不高级”，而是：**它能不能帮你减少重复配置。**

你真正要判断的是三件事：

- 我是不是已经有一个稳定的 OpenAI-Compatible 入口
- 我愿不愿意自己承担中间层带来的调试成本
- 我是不是要把多个模型、多个服务统一收口到一个地址

如果答案都是“是”，这条路就值得走；如果不是，这条路通常只会增加复杂度。

## 🏆 它的核心优势到底是什么

### 1）它是“统一入口”，不是“新 provider”

自定义兼容接口的本质不是新的模型厂商，而是：

- 把已有服务统一成一个兼容 OpenAI 的入口
- 用一个 `base_url` 承接多个模型或多个后端
- 把 Hermes 的接法收敛成固定配置

它的价值在于“收口”，不是“额外能力”。

### 2）它既能接本地，也能接远端

Hermes 官方 provider 文档里明确提供了：

- **Custom Endpoint**
- 通过 `hermes model` 选择 “Custom endpoint”
- 配置会写入 `config.yaml`

这意味着这条路既可以接：

- 本地服务（LM Studio / Ollama）
- 云端聚合层（OneAPI / NewAPI / 企业网关）
- 你自己控制的代理与转发层

### 3）它特别适合做“兼容层迁移”

如果你团队已经在别的工具里广泛使用 OpenAI SDK 或 OpenAI-compatible 配置，这条路的优势很明显：

- 不用重做整套模型切换逻辑
- 不用按 Hermes 原生 provider 一个个重新理解
- 可以先复用现有地址、Key 和模型名，再逐步清理

### 4）它的成本是“调试责任回到你自己”

这也是这条路最大的代价：

- Hermes 不再替你保证某个 provider 的特定细节
- 你的中间层是否支持 Chat Completions、Tools、流式输出、模型列表，都会影响最终体验
- 一旦网关丢字段、改格式、做了不完整兼容，问题就需要你自己排查

所以它适合“已有稳定入口的人”，不适合“第一次上手的人”。

## 🔀 三类自定义兼容入口怎么分

### 1）本地兼容接口：LM Studio / Ollama

这类入口最适合：

- 你主要想本地跑模型
- 你想让 Hermes 连本地推理服务
- 你接受自己管理本地模型加载、端口和性能

#### LM Studio

LM Studio 官方文档明确说明：

- 支持 **OpenAI Compatible Endpoints**
- 可用的基础地址通常是：`http://localhost:1234/v1`
- 支持 `/v1/models`、`/v1/chat/completions`、`/v1/responses` 等接口

这意味着，如果 LM Studio 本地服务已开，你完全可以把它当作一个 OpenAI-Compatible `base_url` 填进 Hermes。

#### Ollama

Ollama 官方文档明确说明：

- 提供 **OpenAI compatibility**
- 默认 OpenAI 兼容入口是：`http://localhost:11434/v1/`
- 使用 OpenAI SDK 时，`api_key` 必填但会被忽略，常用占位值是 `ollama`

这意味着，对 Hermes 来说，Ollama 也可以作为一个自定义兼容接口，只要你模型名、端口和兼容能力准备好了。

### 2）第三方聚合中转层：OneAPI / NewAPI / 聚合池

这类入口最适合：

- 你希望多个上游模型统一收口
- 你想统一结算、限流、权限和监控
- 你已经在其他工具里用同一个聚合地址跑通了

这条路的优点是：

- 同一个 `base_url` 下可切多个模型
- 迁移成本低
- 对团队来说方便统一管理

但注意：

- 聚合层不一定完整支持所有 OpenAI 能力
- Tool Calling、流式输出、图像、嵌入等接口支持度可能不一致
- 你必须自己验证它和 Hermes 的实际兼容性

### 3）企业私有网关：企业安全 / 审计 / 路由

这类入口最适合：

- 企业内网环境
- 有鉴权、日志审计、配额管理要求
- 需要把所有模型请求都纳入统一安全边界

它的价值不是“更强”，而是：

- 可控
- 可审计
- 可统一路由

但它的代价也是最明显的：

- 维护成本更高
- 出问题时排查链路更长
- 兼容层问题会直接反映到 Hermes 上

## 🧰 Hermes 怎么接自定义兼容接口

这里的主线就是：**把现成的 OpenAI-Compatible 入口映射进 Hermes。**

### 1）先搞清三项映射

无论你接本地还是远端，在 Hermes 里最终都要对应这三项：

- `model.base_url`
- `model.api_key`
- `model.name`

你可以把它理解成：

- `base_url` = 你的兼容接口地址
- `api_key` = 你的网关鉴权凭证（本地有时可用占位值）
- `model.name` = 这个兼容层真正识别的模型字符串

### 2）在 Hermes 里选 Custom Endpoint

Hermes 官方文档已经明确给出：

- 运行 `hermes model`
- 在 provider 列表中选择 **Custom Endpoint**
- 配置会写入 `config.yaml`

这条路就是本页真正要介绍的主线。

### 3）LM Studio 的最小理解

如果你接的是 LM Studio，本质上你要映射的是：

- `base_url` → `http://localhost:1234/v1`
- `api_key` → 若你的本地服务未强制校验，可填一个占位值
- `model.name` → 用 LM Studio 实际加载并暴露的模型标识

最小理解可以写成：

```bash
hermes model
# 选择 Custom Endpoint
# base_url 填 http://localhost:1234/v1
# api_key 填占位值或你的本地密钥
# model.name 填 LM Studio 当前服务可识别的模型名
```

### 4）Ollama 的最小理解

如果你接的是 Ollama，本质上映射是：

- `base_url` → `http://localhost:11434/v1`
- `api_key` → `ollama`（官方说明 required but ignored）
- `model.name` → 你在 Ollama 里实际可调用的模型名

最小理解可以写成：

```bash
hermes model
# 选择 Custom Endpoint
# base_url 填 http://localhost:11434/v1
# api_key 填 ollama
# model.name 填本地 Ollama 模型名
```

### 5）聚合层 / 企业网关的最小理解

如果你接的是 OneAPI、NewAPI 或企业私有网关，映射方式同理：

- `base_url` → 你的网关地址（通常以 `/v1` 结尾）
- `api_key` → 你的平台密钥
- `model.name` → 你的网关实际支持的模型名

这一步最重要的不是“看文档写了什么”，而是：

- 你的网关最终暴露的模型名到底是什么
- 它是否真的兼容 `/v1/chat/completions`
- 它是否真的能稳定返回 Hermes 需要的字段

### 6）一定要验证的几件事

无论你接哪一种兼容层，至少都要验证：

- Hermes 能正常进入会话
- 不再提示 `base_url` / `api_key` / 模型错误
- 模型可以正常返回文本结果
- 如果你要用 Tools，兼容层也能正确支持 Tool Calling

如果这里任何一步不通过，你的问题通常不在 Hermes，而在兼容层本身。

## ⚠️ 什么时候先别选它

- 你现在只是想第一次跑通 Hermes，手里也没有现成兼容层
- 你不确定中间层是否真的完整支持 OpenAI 格式
- 你不想处理网关丢字段、模型映射错误、Tool Calling 不完整这类问题
- 你只是想最低门槛开始，而不是复用已有基础设施

## ✅ 这页对自定义兼容接口的默认建议

如果你问我：这一页最该强调什么？

我的结论是：

- 不是先强调“它更高级”
- 而是先强调 **它只适合已经有稳定入口的人**

这条路最值得强调的差异点是：

- 它不是新 provider，而是统一入口
- 它可以接本地、聚合层、企业网关
- 它最省迁移成本，但会把兼容性责任带回给你自己

如果你是下面这类人，这页值得优先看：

- 已经有 OpenAI-Compatible 入口
- 希望 Hermes 直接复用现成路由
- 本地正在跑 LM Studio / Ollama
- 团队里已经有统一模型网关或聚合层

## ⚠️ 常见问题

### 1. 自定义兼容接口是不是比原生 provider 更高级？

不是。

它只是更适合“已有入口的人”，并不意味着更简单，也不意味着体验一定更好。

### 2. 我第一次用 Hermes，应该先选这条吗？

不建议。

如果你没有现成兼容层，优先走 Hermes 已经原生支持的 provider，排查会简单得多。

### 3. 为什么我明明能在别的工具里调用，Hermes 里却不稳定？

常见原因不是 Hermes 本身，而是兼容层存在这些问题：

- 模型名映射不一致
- 返回字段不完整
- Tool Calling 兼容不完整
- 流式输出实现不一致

### 4. 本地服务一定要填 API Key 吗？

不一定要真实鉴权，但很多 OpenAI SDK 风格接口仍然要求字段存在。

例如 Ollama 官方文档就明确写了：

- `api_key` 必填
- 但会被忽略
