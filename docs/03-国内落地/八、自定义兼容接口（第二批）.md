## 1. 这到底是什么

Hermes 官方当前明确写了：**Hermes Agent works with any OpenAI-compatible API endpoint. If a server implements `/v1/chat/completions`, you can point Hermes at it.** 这意味着，只要某个服务暴露了 OpenAI 风格的聊天接口，你就可以把 Hermes 指到这个地址上。
来源：Hermes AI Providers 文档。

这条能力并不是“曲线救国”，而是 Hermes 的 **一等正式能力**。Hermes 的运行时解析文档当前把 `provider: custom` 明确列为 **first-class provider**，而不是临时别名。
来源：Hermes Provider Runtime Resolution 文档。

所以这页讲的不是某一家厂商，而是一种接入方式：

- 本地模型服务
- 自建 GPU 推理服务
- 公司内部代理服务
- 多模型路由器
- 任意第三方 OpenAI-compatible 接口

都可以走这条线。

---

## 2. 什么时候该走 custom provider

这条线适合三种典型场景。

### 2.1 Hermes 官方没有原生 provider

如果你接的服务并不在 Hermes 官方 provider 列表里，但它兼容 OpenAI 接口，那就不需要等待 Hermes 官方专门加 provider，直接走 `provider: custom` 就可以。

Hermes 官方开发者文档还明确提醒：**Hermes can already talk to any OpenAI-compatible endpoint through the custom provider path. Do not add a built-in provider unless you want first-class UX for that service.** 也就是说，除非你特别需要专属登录方式、专属模型目录或非 OpenAI 协议适配，否则完全没必要先等官方加内置 provider。
来源：Hermes Adding Providers 文档。

### 2.2 你用的是本地或自建推理服务

Hermes 官方文档当前直接把这些作为 custom provider 的标准用例：

- Ollama
- vLLM
- SGLang
- LiteLLM Proxy
- 本地 GPU 推理服务
- 任意第三方 OpenAI-compatible API

这说明 custom provider 的首要用途之一，就是“把 Hermes 接到你自己的推理基础设施上”。
来源：Hermes Quickstart、AI Providers 文档。

### 2.3 你要同时管理多个兼容端点

如果你同时有：

- 一套本地测试端点
- 一套公司内网 GPU 端点
- 一套代理到外部厂商的兼容接口

那就更应该走 custom provider，甚至进一步使用 **named custom providers**。Hermes 官方 provider 文档已经给出了 `custom_providers` 的正式配置方式。
来源：Hermes AI Providers 文档。

---

## 3. 什么时候不要优先走 custom provider

这页也要明确告诉用户，**不是所有场景都应该先走自定义兼容接口**。

### 3.1 Hermes 已经原生支持的服务，优先走原生 provider

比如：

- DeepSeek
- GLM / z.ai
- Kimi / Moonshot
- MiniMax
- Alibaba / DashScope / Qwen

这些都已经在 Hermes 官方 provider 列表里。对这类服务，优先走原生 provider 会更清晰，因为：

- provider 名称更规范
- 环境变量更明确
- 后面在 `hermes model`、教程页、解决方案页里更容易统一写法

所以 custom provider 更适合作为 **补位路线**，而不是这些原生 provider 的替代品。
来源：Hermes AI Providers 文档。

### 3.2 你是第一次上手 Hermes

对第一次上手的用户，custom provider 会多出三个变量：

- base_url
- api_key
- model 名称

而且上下文长度有时还要自己确认。对新手来说，这明显比“用 Hermes 原生支持的 provider”更容易出错。

## 4. Hermes 里怎么配置

Hermes 官方当前给了三种正式配置方式。

### 4.1 交互式配置（推荐）

官方 provider 文档写得很清楚：

```bash
hermes model
# Select "Custom endpoint (self-hosted / VLLM / etc.)"
# Enter: API base URL, API key, Model name
```

这条路径最适合第一次接入，因为不需要你先手写 YAML。
来源：Hermes AI Providers 文档。

### 4.2 直接写 `config.yaml`

官方文档给出的标准格式是：

```yaml
model:
  default: your-model-name
  provider: custom
  base_url: http://localhost:8000/v1
  api_key: your-key-or-leave-empty-for-local
```

如果是本地无 Key 服务，可以把 `api_key` 留空；如果是需要认证的兼容服务，就填对应 Key。
来源：Hermes AI Providers 文档。

### 4.3 用环境变量

Hermes 环境变量文档当前明确写了：

- `OPENAI_API_KEY`：用于 custom OpenAI-compatible endpoints
- `OPENAI_BASE_URL`：custom endpoint 的 Base URL

也就是说，对很多简单场景，你甚至可以不立刻手改 config，而是先通过环境变量把兼容端点接上。
来源：Hermes Environment Variables 文档。

## 5. 多个兼容端点怎么管理

如果你只有一条 custom endpoint，用 `provider: custom` 就够了。
但如果你有多条，那应该使用 Hermes 官方文档里的 **Named Custom Providers**。

官方示例是这样的：

```yaml
custom_providers:
  - name: local
    base_url: http://localhost:8080/v1
  - name: work
    base_url: https://gpu-server.internal.corp/v1
    key_env: CORP_API_KEY
    api_mode: chat_completions
  - name: anthropic-proxy
    base_url: https://proxy.example.com/anthropic
    key_env: ANTHROPIC_PROXY_KEY
    api_mode: anthropic_messages
```

然后你可以用三段式切换：

```bash
/model custom:local:qwen-2.5
/model custom:work:llama3-70b
/model custom:anthropic-proxy:claude-sonnet-4
```

这套能力的价值很大，因为它让 Hermes 不只是“接一个兼容接口”，而是可以把多个兼容服务纳入同一套配置体系。
来源：Hermes AI Providers 文档。

---

## 6. `/model custom` 和自动检测怎么理解

Hermes 官方当前还给了一个很实用的细节：

- `/model custom`（不带模型名）会去查询你的 endpoint 的 `/models` API
- 如果这个端点刚好只加载了一个模型，Hermes 会自动选择它

这对本地单模型服务很有用，比如只跑了一个 Ollama 模型或一个 vLLM 单模型实例时，切换起来会更轻。
来源：Hermes AI Providers 文档。

官方 Slash Commands Reference 也明确写了：`/model` 支持 `custom:model`、`custom:local:qwen` 这种语法，并且可以持久化到 `config.yaml`。
来源：Hermes Slash Commands Reference。

## 7. 上下文长度怎么处理

这是 custom provider 最容易被忽略的坑之一。

Hermes 官方 FAQ 和 provider 文档都明确提到：

- Hermes 会尝试从你的服务的 `/v1/models` 端点自动检测上下文长度
- 如果服务返回过低值，或根本不暴露该信息，Hermes 的自动判断可能不准确
- 对 custom endpoint，`hermes model` 会提示你填写 `context_length`，不确定时可以留空自动检测

官方还明确建议，在下面这些场景要手动设置 `context_length`：

- 你用的是 Ollama，并且自定义了更低的 `num_ctx`
- 你想主动把上下文压低以节省显存
- 你的代理服务不暴露 `/v1/models`

对应的写法是：

```yaml
model:
  default: your-model
  provider: custom
  base_url: http://localhost:11434/v1
  context_length: 32768
```

来源：Hermes FAQ、AI Providers 文档。

## 8. 这条线最适合接什么

Hermes 官方当前在“Choosing the Right Setup”里已经给出了一些用例建议：

- 本地模型，简单上手 → **Ollama**
- 生产级 GPU 服务 → **vLLM / SGLang**
- 多 provider 路由 → **LiteLLM Proxy**
- 最大隐私 → 本地 Ollama / vLLM / llama.cpp
- 企业 / Azure 场景 → 通过 custom endpoint 接 Azure OpenAI

这说明 custom provider 的重点不在“替代所有官方 provider”，而在 **承接那些 Hermes 已经能通过 OpenAI-compatible 路线稳定支持的扩展场景**。
来源：Hermes AI Providers 文档。

## 9. 这页最容易踩的坑

### 坑 1：官方有原生 provider，却先走 custom

比如 DeepSeek、GLM、Kimi、MiniMax、Alibaba / DashScope / Qwen 这些都已经有原生 provider。对它们优先走 custom，通常只是增加配置复杂度。

### 坑 2：把兼容接口当成“临时凑合”

对 Hermes 来说，custom provider 不是临时补丁，而是正式支持的接入方式。真正的问题不是“能不能用”，而是你有没有把 base_url、api_key、model、context_length 配对好。

### 坑 3：多个兼容端点却只用一个变量名硬扛

如果你已经有多个兼容服务，强烈建议使用 named custom providers，不要把所有地址都塞进同一个环境变量里。

### 坑 4：把模型名和上下文长度都交给猜测

兼容接口最怕“看起来能跑，实际一到长上下文就炸”。如果你的服务有自定义限制，就老老实实把 `context_length` 写上。
