# 03-提供方与代理

在国内使用 Hermes，真正要解决的通常不是“会不会填 endpoint”，而是“应该先走哪条接入路径”。
如果一开始就把所有路径混在一起，最后往往不是更灵活，而是更难判断问题到底出在哪里。

## Model 和 Provider 的区别

先把这两个概念分开：

- Model 是你最终要调用的模型能力
- Provider 是把模型能力接到 Hermes 的路径

如果这一步没分清，后面很容易把“模型怎么选”和“接入方式怎么接”混成一件事。
模型决定你在能力、成本和适配度上的选择；Provider 决定你通过哪条路径把这些能力稳定接进 Hermes。

所以这页不讨论哪一个模型绝对更强，而是讨论：当你已经有大致模型方向后，接下来该用什么路径把它用起来。

## 四种接入路径分别是什么

在国内环境下，常见会遇到这几类接入路径：

- 官方 Provider：最直接、链路最短、后续判断问题也最清楚
- 代理层：在原始路径之外再套一层，常见于想做统一转发或已有现成接入习惯的人
- OpenAI-Compatible 兼容接口：适合已经有兼容入口，或者后续要统一接更多工具生态的人
- 自建转发 / 中间层：适合已经明确知道为什么需要更高控制权的人

它们之间不是“谁更高级”的关系，而是“谁更适合你当前阶段”的关系。
如果你只是第一次把 Hermes 在国内跑起来，最重要的通常不是灵活性，而是链路简单、问题可判断、后续可持续。

## 默认推荐顺序

默认建议顺序很简单：

1. 先走最直接、最稳定、最少中间层的路径
2. 只有在明确遇到限制时，再考虑代理层或兼容接口
3. 只有在你已经知道自己为什么需要中间层时，才进入更复杂的自建转发

这个顺序的核心不是保守，而是降低排查成本。
如果你一开始就引入太多中间层，后面无论是速度、稳定性，还是调用异常，都更难快速判断是哪一段出了问题。

## 什么时候需要切换路径

只有在这些情况出现时，才值得切换接入路径：

- 当前路径已经无法稳定可用
- 你已经有明确的兼容性要求
- 你需要统一接多个上游模型或服务
- 你已经确认自己需要更高控制权，而不是只是觉得“以后可能会用到”

如果你还处于第一轮上手阶段，大多数情况下不必急着切换。
先让一条简单路径稳定可用，比先做一套看起来很灵活的中间层方案更重要。

## 常见误区

这一页最常见的几个误区是：

- 把 custom endpoint 当成一切问题的默认答案
- 还没跑通就先引入多个中间层
- 没分清 model 和 Provider 就开始调配置
- 把“兼容更多上游”误以为“更适合第一次上手”

如果你只是希望 Hermes 在国内先稳定跑起来，过早复杂化几乎总是副作用大于收益。
