# 从 OpenClaw 迁移到 Hermes：先判断，再迁移

这篇文章解决一个现实问题：如果你已经在用 OpenClaw，现在值不值得迁到 Hermes，以及应该按什么顺序迁，才能避免把自己拖进一次又一次的重构。

---

## 这篇适合谁

- 已经有 OpenClaw 工作流的个人或团队
- 不想推倒重来，只想先迁一个高价值场景
- 想把 Agent 从“聊天”升级成“会执行任务”

## 先判断：你是不是现在就该迁

### 适合马上开始迁的情况

- 你需要终端、文件、网页、浏览器这些执行能力
- 你需要把 Agent 接到 Telegram、Discord、Slack 这类平台
- 你已经明显感觉到现有流程扩展困难

### 不适合立刻迁的情况

- 你现在的 OpenClaw 流程很稳定，而且没有升级动机
- 你没有时间做试点，只能接受零变动
- 你的现有插件体系短期内离不开

结论：不要先问“哪家理念更先进”，先问“是不是已经影响结果”。

---

## 最稳的迁移顺序

### 第一步：先迁基础运行环境

先完成这三件事：
- 安装 Hermes
- 配一个官方 provider
- 跑通一次真实对话

建议先看：
- [快速开始](./quick-start.md)
- [模型与 Provider](./models.md)

### 第二步：只迁一个高价值场景

先挑最容易验证结果的任务，例如：
- 代码库巡检
- 网页信息采集
- 日报生成
- Webhook 通知

不要一上来就迁全部业务。

### 第三步：最后迁团队协作

等单 Agent 稳定后，再迁：
- 多 Agent 分工
- 自动化任务
- 平台通知
- 定时任务

---

## 推荐试点方式

最务实的试点结构：
- 旧系统继续跑生产
- 新系统只接一个低风险流程
- 用 3 到 5 天对比效果

衡量标准不要太复杂，先看：
- 是否更快
- 是否更容易排错
- 是否更容易扩展

---

## 迁移时最容易犯的错

### 错误 1：一上来迁全部插件

结果通常是：
- 成本高
- 过程长
- 没有阶段性结果

### 错误 2：先搭抽象框架，再做业务

正确顺序应该是：
- 先做一个业务闭环
- 再抽取共性结构

### 错误 3：把 custom endpoint 当第一步

Hermes 对很多主流 provider 已经有官方支持，优先走官方路径，而不是先写一大段自定义 YAML。
