# SOUL 管角色，MD 管项目：团队结构详解

当你开始把 Hermes 用到团队协作时，最容易乱掉的不是模型，而是“角色”和“项目资料”混在一起。

这篇文章讲一个简单原则：
- SOUL 负责角色
- Markdown 文件负责项目

---

## 为什么要拆开

如果角色、流程、任务、文档都混在同一个 prompt 里，结果通常是：
- 角色边界模糊
- 上下文膨胀
- 新成员很难接手

更稳的做法是：
- 用 system prompt / SOUL 定义角色
- 用 Markdown 文件沉淀项目事实

---

## SOUL 应该管什么

角色层应包含：
- 这个 Agent 是谁
- 它负责什么
- 它不负责什么
- 它输出风格是什么
- 它的工作边界是什么

例如：
- PM 负责拆目标和控范围
- Coder 负责实现
- Reviewer 负责检查
- Content 负责对外表达

---

## Markdown 文件应该管什么

项目层应包含：
- 当前目标
- 范围
- 决策
- 任务清单
- 阶段结论
- 交付物清单

这类内容应该可追溯、可阅读、可交接，而不是只存在聊天记录里。

---

## 一个最实用的分工方式

- system prompt：定义人设和职责
- PROJECT.md：项目目标
- TASKS.md：执行清单
- DECISIONS.md：关键取舍
- CHANGELOG.md：对外交付变化

这样做的价值是：
- 角色稳定
- 项目内容可追踪
- 后续更容易扩展到多 Agent

---

## 常见错误

### 错误 1：把项目事实全写进人设

结果是 prompt 越来越臃肿，后续任何变动都很难维护。

### 错误 2：把角色说明写进任务文档

结果是任务文档变成半个 system prompt，边界混乱。
