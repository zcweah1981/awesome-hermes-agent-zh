# 03-敏捷 Web 开发助手

> 一句话定位：这个方案帮助想做后台、控制台、表单系统或内部 Web 工具的人，把一个想法快速压成可开工的页面结构、接口草案与代码骨架。

---

## 1. 这是什么方案

### 核心场景
这个方案适合你已经知道自己想做一个什么 Web 工具，但不想先自己从零拆页面、拆数据、拆接口、拆前后端边界。

### 最终结果
你最后会先拿到一版可开工的 Web 原型骨架，包括：
- 页面清单
- 关键交互流
- 数据结构草案
- 接口草案
- 前端目录骨架
- 第一批文件建议

### 页面定位
这是一个可直接应用的方案页，不是教程页，也不是概念页。它的目的不是教你学会所有 Web 开发知识，而是帮你先把一个 Web 工具推进到“能开始搭代码”的状态。

---

## 2. 适合谁

### 适合谁
- 想快速搭一个内部管理后台的人
- 想先把 Web 工具 MVP 跑起来的产品 / 运营 / 开发
- 已经有明确业务目标，但不想先手工拆全栈结构的人

### 更适合什么阶段的人
- 新手先跑通：先把想法压成一版能开工的后台骨架
- 已经有基础、想提效：减少自己拆页面、拆接口、拆目录的时间
- 小团队开始协作：先把页面、接口、角色边界压清楚，再多人接力推进

---

## 3. 你要准备什么

### 最少准备项
- 一个明确的 Web 工具场景
- 一句能说清楚目标用户和核心动作的话
- 一轮愿意先用 mock 数据验证的心态

### 标准输入
- 你到底想做什么系统
- 最小要做哪几个页面
- 哪些字段、状态、操作最关键

### 标准输出
- 页面清单
- 页面结构和操作流
- 数据结构草案
- 接口草案
- 前端目录骨架
- 第一批文件建议

## 5. 默认推荐

### 默认入口
- CLI / ACP

### 默认模型
- 默认推荐：偏代码与结构化能力强的模型
- 备选推荐：能稳定输出页面结构、接口草案和目录建议的通用模型

### 默认使用方式
默认先用 CLI 跑第一轮，把需求压成页面、数据、接口、目录与首批文件建议。确认方向对了以后，再进入 ACP 在编辑器里继续补页面文件、service、状态管理和 mock 数据。

### 默认实现方式
- 默认 Profile：`webdev-lab`
- 默认 SOUL：敏捷 Web 产品与实现专家
- 默认 SKILL：`agile-web-development-assistant`
- 是否需要脚本：首版默认不依赖脚本，先用人工可验证的单轮输入输出跑通

## 6. 5 分钟跑通

### 用户怎么使用
1. 先把你的 Web 工具目标说清楚
2. 让 Hermes 先拆页面、数据、接口和目录骨架
3. 检查结果有没有把最小可开工结构压出来
4. 再给第二轮续跑指令，让它开始往真实文件走

### 最小触发方式
- 命令 / CLI 输入示例：

```text
我想做一个销售线索管理后台。
请先把这个需求压成第一版可开工 Web 原型，要求：
1. 先给出最小页面清单
2. 先给出每个页面负责什么
3. 先给出数据结构草案
4. 先给出接口草案
5. 先给出前端目录骨架
6. 先给出第一批应该生成的文件
7. 默认先用 mock 数据，不接真实后端
```

### 跑通后你会看到什么
- 一版页面清单，例如：线索列表、线索详情、跟进记录、新建线索、统计概览
- 一版接口草案，例如：获取线索列表、详情、筛选查询、提交跟进、统计概览
- 一版目录骨架，例如：`pages/`、`components/`、`services/`、`stores/`、`utils/`
- 一版第一批文件建议，例如：`router.ts`、`pages/lead-list`、`pages/lead-detail`、`services/lead.ts`

## 7. 超级个体版 / 团队协作版

### 超级个体版

#### 定义
一个人先把这件事独立推进到“能开始搭后台代码骨架”的状态。

#### 最小流程
1. 先给 Hermes 一个明确的后台场景
2. 先拿到页面、数据、接口、目录骨架
3. 再给第二轮指令，让它补首批页面文件和 service
4. 最后只检查最小链路能不能跑通

#### 交付结果
- 最终拿到什么：一版可开工的 Web 原型结构包
- 哪一步需要人工确认：页面是否够最小、接口是否合理、第二轮续跑顺序是否符合你的开发习惯

### 团队协作版

#### 是否建议首批上线
- 建议

#### 最小角色
- 角色 1：需求 / 产品
- 角色 2：前端 / Builder
- 角色 3：后端 / API
- 角色 4：测试 / QA

#### 最小交接顺序
1. 需求角色先产出页面清单、状态说明、操作流
2. 前端角色接手页面骨架、目录和首批文件建议
3. 后端角色接手数据结构与接口约定
4. 测试角色确认最小链路、风险点和是否能开工

#### 团队版交付物
- 中间产物 1：页面结构与操作流
- 中间产物 2：接口草案与目录骨架
- 最终交付物：团队可开工的 Web 原型实施包

## 8. 模板与下一步

### 可直接复制的模板
- 输入模板：

```text
我想做一个【场景名】Web 工具。
目标用户是【谁】。
他们最常做的动作是【动作 1 / 动作 2 / 动作 3】。
请先把这个需求压成第一版可开工 Web 原型，输出：
1. 页面清单
2. 页面职责
3. 数据结构草案
4. 接口草案
5. 前端目录骨架
6. 第一批文件建议
7. 第二轮续跑建议
```

- 输出模板：
  - 页面清单
  - 页面职责
  - 数据结构草案
  - 接口草案
  - 目录骨架
  - 第一批文件建议
  - 下一句续跑指令

- 检查清单：
  - 页面有没有拆清楚
  - 数据和接口有没有先占位
  - 目录和文件有没有能直接开工
  - 第二轮续跑有没有明确顺序

- 团队交接模板：
  - 产品先交页面和状态流
  - 前端再交骨架和首批文件
  - 后端补接口与字段
  - QA 最后给是否能开工的判断
