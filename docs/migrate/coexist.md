# OpenClaw 与 Hermes：先共存，再替换

不是所有团队都适合直接迁移。

如果你的 OpenClaw 工作流还在跑生产、现有插件链还没法立刻替换，最稳的办法不是硬切，而是先共存：让 OpenClaw 继续承担稳定生产部分，让 Hermes 先接更容易验证价值的新任务。

## 适合先共存的情况
- 旧系统已经接入真实业务，短期停不了
- 现有插件或 Bot 逻辑改动成本很高
- 你需要先证明 Hermes 的价值，再争取迁移资源

## 推荐共存边界

### 继续留在 OpenClaw 的部分
- 已经稳定跑生产的插件链
- 短期无法替换的历史 Bot 流程
- 依赖旧平台绑定逻辑的自动化环节

### 优先交给 Hermes 的部分
- 仓库巡检与文档整理
- Web 搜索、网页提取、浏览器操作
- 多 Agent 任务拆分
- Telegram / Discord / Slack 消息协作
- 新增但尚未进入生产的试点流程

## 共存的最小执行法
1. 不改旧系统主链路
2. 只挑一个新增或低风险流程给 Hermes
3. 为两套系统设清晰边界：输入、输出、负责人、回滚条件
4. 连续观察 3 到 5 天，再决定是否扩大范围

## 常见错误
- 一边说共存，一边偷偷做全量替换
- 没有定义回滚条件
- 没有明确谁负责哪个系统
- 拿抽象概念比较，没拿真实任务比较

## 完成标志
- 你已经明确哪些任务继续留在 OpenClaw
- 你已经选出第一个交给 Hermes 的试点流程
- 你已经定义试点周期与回滚条件
