# Hermes 中文站内容标准规范

> 用途：这是 Hermes 中文站新增、重写和验收内容的统一标准文档。所有 P0/P1/P2 内容生产、治理记录、配图制作和发布前检查，都必须先符合本规范，再进入验收与部署。

## 0. 适用范围

本规范适用于：

- `docs/**/*.md` 普通教程、实战文章、最佳实践、国内入口、现成方案和参考页。
- 新增或重写文章的正文结构、标题、导语、链接、代码块和验收清单。
- 文章 metadata、版本、发布批次、来源状态等治理信息。
- `.webp` 首图、结构图、流程图、对比图、真实截图和输出物总览图。
- dispatch-system 派单时写入任务卡的内容约束。

本规范不用于保存内部 PM 派单日志、临时执行看板、调试输出或私有凭据。

## 1. 内容定位

- 优先写“真实应用场景”，不要写大而全的功能说明书。
- 每篇只解决一个明确问题：读者是谁、正在卡什么、看完能做成什么。
- 标题要直给：`实战：...`、`教程：...`、`...助手`、`...接入`，避免空泛概念标题。
- 正文默认中文，语气要像经验丰富的朋友带路：先给结论，再解释原因，再给步骤。
- 文章面向初学者、非专业用户和刚开始试 Hermes 的读者；默认读者不知道 Agentic Workflow、MCP、Cron、Skill、Memory 等术语。
- 表达必须通俗、连续、像一篇可读文章，不像产品说明书、验收报告、任务草稿或功能清单。
- 不把 Hermes 描述成万能工具；必须说明适合谁、不适合谁、前提条件和失败排查入口。
- 新内容必须与已有文章去重：能链接旧文就链接旧文，不重复讲基础概念。

## 2. 文件位置与命名

- 新增实际应用文章优先放在 `docs/01-从这开始/05-实战应用/` 或对应的现有栏目下。
- 如果是“现成方案 / 助手 Pack”，放在 `docs/02-现成方案/...` 对应分类下。
- 如果是国内入口、云厂商、模型供应商或部署落地内容，放在 `docs/03-国内落地/...`。
- 文件名使用中文标题，保留现有编号风格，例如：`23-实战：服务器自动化运维.md`。
- 同一目录内编号必须连续，不抢占已有编号。
- 图片资源优先放在 `docs/assets/`；如果属于某个国内落地子目录的操作截图，可放在该目录下的 `assets/`。

## 3. 正文 metadata 与治理文档

### 3.1 普通正文禁止 frontmatter

普通 `docs/**/*.md` 教程、实战、最佳实践、国内入口文章，默认 **不得新增 frontmatter**。

禁止在正文开头出现这类会被 GitHub Preview 渲染出来的 metadata 块：

```markdown
---
title: "..."
description: "..."
---
```

禁止在正文中保留这些模板残留：

- `## 标题`
- `## 正文草稿`
- `H2:` / `H3:` 这类提示词痕迹
- `待补充链接`
- `https://user-images.githubusercontent.com/12345/...` 这类占位图片 URL
- 真实 token、secret、手机号、私人群名、公司内部信息

只有确实继续维护已有第三方聚合页，且该栏目历史上已经使用 frontmatter 时，才允许沿用旧结构；新增普通内容不得仿照。

### 3.2 metadata 统一进入治理文档

文章的机器可读信息不写在正文里，统一放在治理文档中维护：

- `governance/site-route-map.yaml`：页面路由、标题、摘要、模块、栏目、排序、发布状态。
- `governance/version-ledger.yaml`：与 Hermes 上游版本相关的同步记录和受影响页面。
- `governance/content-release-ledger.yaml`：P0/P1/P2 内容批次、审核状态、测试状态、提交 hash、部署状态。
- `governance/content-contract.md`：长期字段合同和新增页面流程。

新增或重写文章时，正文和治理记录必须同时更新。正文只负责读者阅读体验；治理文档负责站点索引、版本、摘要、发布状态和维护追踪。

建议治理记录字段：

```yaml
- source: docs/01-从这开始/05-实战应用/23-实战：个人项目开发工作流.md
  slug: /start/practical/personal-dev-workflow
  title: 实战：将 Hermes Agent 融入个人项目开发工作流
  description: 面向个人和独立开发者，展示如何用 Hermes Agent 串联需求、编码、审查、文档和监控。
  module: start
  section: 实战应用
  order: 23
  status: published
  updated: "2026-07-05"
  source_type: original
  nav_group: practical
  content_release: 20260705-p0-actual-apps
  review_status: pm-reviewed
```

## 4. 标准文章结构

文章必须像“带读者走一遍”的文章，而不是“目标 / 核心信息 / 正文草稿”的说明书。推荐结构：

1. `# emoji + 编号 + 中文标题`，例如 `# ⚡ 21-Hermes Agent + Ollama：本地部署最快路径`。
2. 一句话速答 / 一句话先说清楚；这一段替代 metadata 摘要，必须是自然正文。
3. 首图或主结构图。
4. `## 👀 适合谁`：用 3-5 条读者场景，不写抽象人群标签。
5. `## 🎯 先看结论` / `## 📌 先记住核心判断`：先把读者最该记住的判断讲清楚。
6. `## 🧭 最短路线` / `## 🚦先选哪一种`：给出最少步骤、选择条件或路线图。
7. `## 🛠️ 具体怎么做`：进入真实步骤，每一步都包含“做什么、为什么、看到什么算成功、失败先查什么”。
8. `## 🧩 真实场景 / 工作流拆解`：用故事或场景把步骤串起来，不要只列功能。
9. `## ⚠️ 常见坑` / `## 边界与风险`：告诉初学者哪里最容易误解。
10. `## ✅ 过关标准`：用可检查的结果判断文章是否跑通。
11. `## ➡️ 下一步`：固定导航块，指向下一篇和栏目总览。
12. `## 📖 出处`：如内容基于官方文档、社区文章、开源项目或案例，必须列明来源。

不是每篇都必须完全一致，但每篇至少要有：

- 一句话结论。
- 适合谁 / 不适合谁。
- 前提条件。
- 最短路径。
- 具体步骤或真实工作流。
- 可复制命令、配置或 Prompt。
- 成功判定。
- 常见坑或排错入口。
- 下一步导航。
- 出处或“本文为原创整理，无外部案例来源”的说明。

禁止把文章写成以下结构：

```markdown
## 标题
## 适合谁
## 目标
## 核心信息
## 正文草稿
```

这种结构是派单草稿，不是最终文章。最终文章要把“目标”和“核心信息”融入导语、结论和正文叙事里。
## 5. 标题、导语、层级与 emoji

- H1 只出现一次，必须直接承担文章公开标题；不要再加 `## 标题` 重复展示。
- H1 延续既有文章风格：编号 + 主题 + 直给场景，可带稳定 emoji，例如 `# ⚡ 21-Hermes Agent + Ollama：本地部署最快路径`。
- H1 下方第一段必须是自然导语，推荐以“**一句话先说清楚：**”或“**这页只讲一件事：**”开头；不要显示 `description:` 这类字段名。
- H2 用来分主段落，H3 用来分步骤或模式。
- 新文章必须使用 emoji 区分关键段落，保证中文用户快速扫读时能立刻识别段落功能。
- emoji 不是装饰，而是阅读路标；每个 H2 优先使用一个稳定含义的 emoji。
- 延续现有风格，优先使用：`👀` 适合谁、`🎯` 目标/为什么、`🧭` 最短路线、`🚦` 选择判断、`📦` 产出物、`⚡` 快速上手、`✅` 验收/成功标准、`🧩` 结构拆解、`🖼️` 配图/截图、`🛠️` 操作步骤、`⚠️` 常见坑、`🔗` 相关链接。
- 同一篇文章内 emoji 语义要一致，不要为了花哨频繁更换。
- 每个主段落开头先给一句“这一节解决什么”，再展开细节，避免中文读者在长文中迷路。
- 表格用于选择、对比、产出清单；不要用长表格堆砌百科信息。
- 代码块必须标注语言：`bash`、`yaml`、`dotenv`、`markdown`、`text`。

## 6. 初学者表达与文章感

- 默认读者是第一次接触 Hermes 的普通用户，不是 Agent 工程师；不要上来堆术语。
- 每个专业词第一次出现时必须用一句白话解释，例如：`Skill` 可以解释为“把你反复做的事存成一套可复用步骤”。
- 文章要有连续叙事：先说痛点，再说这篇只解决什么，再带读者做一遍，最后告诉他做到什么程度算成功。
- 不要把小标题写成“目标 / 核心信息 / 正文草稿”；这些是编辑工作流字段，不是面向读者的文章结构。
- 少用抽象句：例如“提升 Agent 自主性和可靠性”；改成“让 Hermes 少问你、少打扰你，但出问题时能拿出证据”。
- 少用长列表堆概念；如果必须列清单，每个清单后要接一句“这对你意味着什么”。
- 代码和配置前必须先说“这段是做什么的”；代码后必须说“成功时你会看到什么”。
- 一篇文章只让读者记住 1 条主线，不要把多个主题硬塞到一起。

## 7. 链接、安全与引用

- 站内链接使用相对路径。
- 中文文件名中的空格在链接中使用 `%20`，沿用现有写法。
- 相关内容不要重复讲，应该链接到已有权威页。
- 涉及密钥、Token、Secret 时，只写变量名和占位值，不给真实值。
- 不得泄露真实邮箱、手机号、聊天群名、服务器 IP、公司内部系统地址或私有路径。
- 外部来源必须可公开访问；如果来源不稳定，应在治理文档中标注来源状态。

## 8. 下一步导航与出处

### 8.1 下一步固定格式

每篇文章底部必须有 `## ➡️ 下一步`，格式统一：

```markdown
---

## ➡️ 下一步

完成后进入：
[下一篇标题](./下一篇.md)

如果你想先回到上一阶段入口重新确认位置：
[栏目总览](./01-总览.md)
```

要求：

- “完成后进入”必须指向同栏目下一篇或最合理的后续文章。
- “回到上一阶段入口”必须指向该栏目总览或上一级总览。
- 链接必须是真实存在的相对路径，不允许留空或写占位。
- 如果文章不是线性教程，也必须给出“下一篇推荐读什么”和“回到哪里重新选路线”。

### 8.2 出处固定格式

如果文章引用了官方文档、社区文章、开源项目、视频、X/Substack/博客案例，底部必须有 `## 📖 出处`：

```markdown
---

## 📖 出处

本文基于以下来源做了原创中文整理：

- Hermes 官方文档 — [标题](https://example.com)
- 社区案例作者 — [标题](https://example.com)（平台 / 协议 / 备注）
```

要求：

- 有出处就必须列出处；不能只在正文中零散提到。
- 如果基于开源项目，必须写项目名、链接和协议（如已知）。
- 如果基于官方文档，必须写“官方文档 — 标题”。
- 如果是原创经验，没有外部案例来源，可以写：`本文为原创经验整理，未引用外部案例；相关功能说明参考 Hermes 官方文档。`
- 出处用于公开透明，不替代治理文档中的 `source_refs` / `source_review`。

## 9. 图片总原则

- 每篇新文章至少 1 张主图；重点实战文章建议 2-3 张图。
- 图不是装饰品，必须承担解释任务：路径图、结构图、对比图、流程图、真实截图证据。
- 首图应放在开头速答之后，用来让读者一眼理解文章主线。
- 结构图、流程图、对比图必须使用生图模型生成，不允许用 SVG/HTML/CSS/Mermaid 自己手绘后导出。
- 所有新增图片必须是 `.webp`，不新增 `.png`、`.jpg`、`.jpeg`、`.svg`。
- 图片文件名使用英文小写短横线，带主题和版本号，例如：
  - `actual-dev-workflow-mainline-v1.webp`
  - `server-devops-alert-flow-v1.webp`
  - `agent-philosophy-healthy-silence-v1.webp`
- 图片 alt 文本必须是中文长描述，说明图里表达的关系，不要只写“截图”或“流程图”。
- 如果生图能力不可用，可以临时复用仓内已有 `.webp`，但必须在验收报告中说明复用原因，且不能留下占位外链。

## 10. 结构图 / 流程图视觉风格

基准图：`docs/assets/practical-v2-02-ollama-local-model.webp`。后续实战结构图必须复刻它的“深色电路板架构图”语言，而不是泛科技发光节点图。

- **画幅**：优先 16:9 横图，推荐 1600×900 或 1376×768；复杂大图可用 2752×1536。
- **构图**：使用“中央核心模块 + 周边功能模块/对照卡”的架构图布局；信息关系要像系统设计图，不要做星图、脑图、雷达图、粒子网络或随机 hub-and-spoke。
- **背景**：深蓝黑或近黑背景，叠加克制的细网格/电路板纹理；背景只提供蓝图感，不要星空、强粒子、强光晕或海报渐变。
- **主色**：前景以白色/浅蓝白为主，模块边框、文字、连线保持高对比；浅蓝灰只用于标题条或少量模块填充。
- **辅助色**：只用少量橙色/琥珀色实心圆点作为连接器或关键触发点；绿色只用于“健康/成功”状态，不做大面积装饰。
- **节点**：统一圆角矩形。大模块是白色细边框容器；内部子模块是深蓝灰填充 + 白色边框；“对照卡”可用浅蓝灰标题条；核心模块边框略粗，内部要有芯片/电路/路由中枢线框图标。
- **连线**：使用白色或浅蓝白 1-2px 直角折线，模拟 PCB 电路走线；连接点和转折重点放 6-8px 橙色圆点；避免霓虹粗线、曲线蛛网和杂乱箭头。
- **布局**：模块分布要平衡，左右/上下留白充足；流程图可以从左到右，但仍要保持电路走线和容器层级；对比图用左右大容器 + 中央路由/判断模块。
- **字体**：现代无衬线中文字体，白色文字；图片内文字短、粗、清楚。主标题最大，核心模块次之，子模块标签更小；禁止整段说明。
- **图标**：统一白色线框图标，主题明确；核心模块图标更复杂，其它模块图标简洁。不要人物、吉祥物、3D 图标、彩色贴纸或装饰性图标堆砌。
- **可读性**：一张图只表达一个核心系统关系；读者 5 秒内能看懂主线。

生图提示词必须明确包含：

```text
16:9 dark circuit-board architecture diagram, deep blue-black background with subtle fine grid, central Hermes routing hub module, surrounding rounded rectangular system modules and comparison cards, white thin borders, dark blue-gray card fills, clean white Chinese typography, PCB-style right-angle connector lines in white or pale cyan, small orange circular connection nodes at endpoints and turns, white outline icons, balanced technical documentation layout, minimal glow, readable, professional, similar style to practical-v2-02-ollama-local-model.webp
```

负面约束：

```text
no cartoon characters, no hand-drawn style, no SVG export look, no neon spider web, no random particle network, no star map, no colorful gradient poster, no 3D mascot, no photorealistic people, no tiny unreadable text, no messy arrows, no decorative-only image, no large glowing cyan borders
```

## 11. 图片类型标准

### 11.1 主结构图 / 路径图

适合文章开头。

要求：

- 16:9 横图优先。
- 展示完整闭环，而不是孤立模块。
- 文案短，节点少，读者 5 秒内能看懂。
- 适合 P0 实战文章。

示例风格：

- `rm2-2-get-running-index-06-stage-map-closed.webp`
- `solution-practical-03-github-backup-cron-v1.webp`
- `practical-v2-05-github-pr-review.webp`

### 11.2 对比图

适合解释选择。

要求：

- 左右两栏或三栏对比。
- 每栏只放关键差异。
- 必须配正文解释“看这张图时抓哪两个判断点”。

示例风格：

- `solution-webdev-solo-vs-team-map-v1.webp`
- `solution-xhs-cli-vs-acp-v3-cliproxy-g31.webp`
- `rm2-4-soul-02-soul-behavior-diff.webp`

### 11.3 真实截图 / 操作证据

适合云厂商、企业微信、桌面端、终端验证。

要求：

- 截图中不能出现真实 token、secret、手机号、私人群名等敏感信息。
- 截图必须对应正文中的某一步。
- 正文必须说明这张图证明什么。
- 如果截图来自官方页面，要在正文说明“官方截图/官方入口”。

示例风格：

- `tencent-server-list-login-entry.webp`
- `wecom-create-bot-entry-official.webp`
- `desktop-07-real-chat-v1.webp`

### 11.4 输出物总览图

适合“现成方案”类文章。

要求：

- 展示用户最终拿到什么。
- 最好拆成 3 个阶段：输入 → 处理 → 产出 / 下一步。
- 不要只做漂亮海报，要能帮助读者判断是否值得用。

示例风格：

- `solution-webdev-3-layer-map-v1.webp`
- `solution-message-summary-output-map-v1.webp`
- `office-daily-output-gemini-3-pro-image-preview.webp`

## 12. 图片数量建议

- P0 实战长文：3 张
  1. 首图：端到端闭环图
  2. 中段：关键选择 / 架构对比图
  3. 后段：输出物或验证结果图
- P1 教程：2 张
  1. 首图：路径图
  2. 中段：步骤或产出结构图
- 小更新 / 参考页：0-1 张，不强行配图。
- 如果无法获得真实截图，优先画结构图，不要编造“真实界面”。

## 13. 图片引用格式

示例：


## 14. 内容质量验收清单

每篇文章交付前必须自查：

- 是否与现有 SOUL / Ollama / MCP / Skills / Memory 等文章重复？
- 是否有明确读者画像？
- 是否有真实场景，而不是功能罗列？
- 是否像一篇连续文章，而不是“目标/核心信息/正文草稿”的说明书？
- 是否默认面向初学者，用白话解释了第一次出现的专业词？
- 是否有最短路径？
- 是否有可复制命令、配置或 Prompt？
- 是否说明成功标准？
- 是否说明失败时查哪里？
- 是否有固定格式的 `## ➡️ 下一步`，且链接真实存在？
- 如有外部来源，是否有固定格式的 `## 📖 出处`？
- 是否引用已有文章而不是重复讲？
- 是否至少有 1 张有解释价值的 `.webp` 主图？
- 图片 alt 是否具体、中文、可读？
- 是否未泄露任何 token、secret、手机号、私有路径？
- 是否没有 frontmatter、`## 标题`、`## 正文草稿` 或占位图片 URL？
- 是否已同步更新治理文档中的 metadata / route / release 记录？

## 15. 发布前治理检查

新增或修改公开内容后，发布前必须检查：

- `governance/site-route-map.yaml` 是否包含新增页面。
- `source` 是否指向真实存在的 Markdown 文件。
- `slug` 是否稳定、可读，不包含本地路径。
- `title` 和正文 H1 是否语义一致，但不要求完全逐字相同。
- `description` 是否是站点摘要，不应复制正文第一段的长篇内容。
- `order` 是否与目录编号一致。
- `status`、`updated`、`source_type` 是否已更新。
- 本批次是否写入 `governance/content-release-ledger.yaml` 或同等发布记录。
- 如果涉及上游版本、命令、配置、API 或部署，是否写入 `governance/version-ledger.yaml` 或来源复核记录。
